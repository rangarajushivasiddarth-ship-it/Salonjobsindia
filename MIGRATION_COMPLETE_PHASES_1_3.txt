Phase 2: Dual-Write Adapter (✅)
--------------------------------
File: lib/adapters/dual-write-adapter.ts (323 lines)

Architecture:
- Writes to MongoDB first (primary during migration)
- Then writes to Supabase (target)
- Automatic retry of failed Supabase writes
- Full audit trail in sync_logs

Functions:
1. createJobDualWrite(jobData)
   - Creates job in both DBs atomically
   - Returns: { mongodb, supabase, status }
   - Status: 'full_success', 'partial_success', 'mongodb_only'

2. updateJobDualWrite(jobId, updates)
   - Updates job in both DBs
   - Tracks changes in sync_logs
   - Automatic retry logic

3. approveJobDualWrite(jobId, adminId, expiresAt?)
   - Atomic approval: status PAYMENT_PENDING → LIVE
   - paymentStatus: pending → approved
   - isVisible: false → true
   - visibility: private → public

4. retryFailedWrites()
   - Checks sync_logs for failed writes
   - Retries Supabase writes if failed
   - Updates sync status on success

Data Normalization:
- MongoDB format ↔ PostgreSQL format
- Handles: nested objects, arrays, dates
- Automatic conversion in both directions

CURRENT ARCHITECTURE (PHASES 1-3):
===================================

Salon Owner Creates Job:
  1. Submits via salon owner UI
  2. POST /api/sync (type='job-payment')
  3. createJobDualWrite() executes:
     - Write to MongoDB (Job collection)
     - Write to Supabase (jobs table)
     - Log sync event to sync_logs
  4. Status: PAYMENT_PENDING (in both DBs)
  5. Returns: jobId, paymentId, dualWriteStatus

Admin Approves Job:
  1. Views /admin/pending-jobs
  2. Gets jobs where status='PAYMENT_PENDING'
  3. Clicks approve
  4. PUT /api/sync (approve job)
  5. approveJobDualWrite() executes:
     - Update MongoDB: status→LIVE, paymentStatus→approved, isVisible→true
     - Update Supabase: same fields
     - Log approval to sync_logs
  6. Status: LIVE (in both DBs)

Job Seeker Searches:
  1. GET /api/jobs (job seeker search)
  2. Queries: status='LIVE', isVisible=true, paymentStatus='approved'
  3. From BOTH DBs (configurable via routing):
     - Primary: Supabase (after Phase 5)
     - Fallback: MongoDB (during migration)
  4. Returns: live approved jobs

SINGLE SOURCE OF TRUTH:
- Status PAYMENT_PENDING: Admin query target
- Status LIVE: Seeker visibility requirement
- isVisible flag: Additional seeker filter
- paymentStatus: Approval gate (approved = can go live)

TECHNICAL DETAILS:
==================

Unified Status Lifecycle:
DRAFT
  ↓
PAYMENT_PENDING (payment submitted, awaiting admin approval)
  ↓
APPROVED (admin approved payment, job ready for publication)
  ↓
LIVE (job published, visible to job seekers)
  ↓
EXPIRED (30-day expiration reached)
  ↓
CLOSED (manually closed by owner)

Payment Status Enum:
- none: No payment submitted yet
- pending: Payment submitted, awaiting admin review
- approved: Admin approved payment
- rejected: Admin rejected payment

Visibility Rules:
- Admin sees all jobs (admin RLS policy)
- Salon owner sees own jobs (owner RLS policy)
- Job seeker sees: status='LIVE' AND isVisible=true AND paymentStatus='approved'
- Public sees only LIVE jobs with is_visible=true

Database Sync Tracking:
- Every create/update logged to sync_logs
- Tracks source: 'mongodb' vs 'supabase' vs 'dual-write'
- Tracks status: 'success', 'failed', 'pending'
- Full data snapshots: old_data, new_data (JSONB)
- Automatic retries for failed Supabase writes

Zone of Safety:
- MongoDB remains primary writer until Phase 6
- Supabase reads can start Phase 5
- Dual-write ensures both DBs stay in sync
- sync_logs provide audit trail for troubleshooting
